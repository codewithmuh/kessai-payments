Kessai (決済, "payment") is a small wallet payments service in yen, built the way a payments team would build it: three Availability Zones in Tokyo and a disaster-recovery copy in Osaka. Then it goes through 12 failure drills, and every drill is scored the same way: how many acknowledged payments were lost, and how long recovery took.

  1. 1

    Sato's wallet app → Kessai

    The payment is asked for, with a key

    The app sends the amount in whole yen, with the tax split by rate: 10 % for the latte drunk in the café, 8 % for the cookies taken away. It also sends an Idempotency-Key, a name for this one attempt to pay, so that a retry can never become a second payment.

    POST /v1/payments · Idempotency-Key
  2. 2

    Inside Kessai

    One transaction: all of it, or none of it

    Kessai locks Sato's wallet row, checks the balance covers ¥1,200, then writes everything in one PostgreSQL transaction: the payment, two ledger entries that sum to zero, the key with the response it will return, and the event for the merchant. If any part fails, none of it happened.

    SELECT … FOR UPDATE · COMMIT
  3. 3

    Kessai → the app

    201: acknowledged, and written down outside AWS

    Aurora confirms a commit only once four of its six storage copies, spread over three AZs, have it. So the 201 means the payment is durable. In a drill, the payment client runs outside AWS and logs every 201. From that moment on, a payment missing from the database counts as lost.

    201 Created · acks.log
  4. 4

    The app → Kessai, again

    A retry gets the same answer, not a second charge

    Now suppose the 201 got lost: the phone dropped signal, or the database failed over mid-reply. The app retries with the same key. Kessai finds the key, sees the same body, and replays the saved response. The ledger does not move. The same key with a different body is refused.

    same key + same body → the saved response
  5. 5

    Kessai → the merchant

    The merchant hears about it, once in effect

    The event was committed with the payment, so it cannot be lost. A relay moves it to an SQS FIFO queue, and a sender delivers a signed payment.succeeded webhook, retrying while the merchant answers 503. Delivery is at least once, so the merchant deduplicates by event id.

    outbox → SQS FIFO → signed webhook
  6. 6

    Every night

    The books meet the bank

    A daily job compares the ledger with the mock bank's settlement file. Every entry ever written must still sum to ¥0, and every top-up must match money the bank actually saw. Any difference raises an alert.

    reconcile · CronJob · daily

Why it exists

Anyone can draw a resilient system. This one gets measured.

Kessai exists to prove, with numbers, that a payments backend on Amazon EKS loses no acknowledged payment and never charges twice. Payments make those numbers easy to read: losing a payment, or charging one twice, is the clearest data-loss failure there is, so "0 payments lost" needs no explanation.

A reference payments service

Top-ups, payments and refunds in yen, a double-entry ledger, signed webhooks and daily reconciliation, following public rules: Stripe's API conventions and Japan's tax guidance.

Production-grade on AWS

EKS over three Tokyo AZs, Aurora PostgreSQL, SQS, Argo CD and Terraform, a pilot-light copy in Osaka, and backups in a separate, locked account.

Broken on purpose

12 failure drills, from killing pods to losing the whole Tokyo region, each modelled on a real incident and injected with AWS Fault Injection Service.

Scored with numbers

Every drill counts the acknowledged payments lost (RPO) and times recovery (RTO), then gets a runbook and a postmortem. Results replace targets here as they land.

Small on purpose

Who it's for

Engineers learning how payment systems stay correct when things fail, hiring teams who want proof instead of claims, and anyone following the build on CodeWithMuh.

Money rules

Seven rules that every test and every drill checks.

Payments go wrong in a few well-known ways: amounts that drift, balances that go negative, retries that charge twice, events that vanish, books that disagree with the bank. Each rule closes one of them.

  1. R1

    Integer yen

    No floats anywhere. The yen has no minor unit, so ¥1,200 is stored as the integer 1200.

    Integer columns; floats banned in the money code.

  2. R2

    Double-entry

    Every movement writes balanced entries. Add up every entry ever written and you get ¥0.

    Written in the same transaction as the movement; checked in tests and after every drill.

  3. R3

    Never below ¥0

    A wallet cannot spend money it does not have, even when 200 payments arrive at once.

    A row lock or a conditional update in the same transaction.

  4. R4

    One key, one payment

    Same key and body: the saved response. Same key, different body: an error. Keys are kept 24 hours.

    The key is stored in the same transaction as the payment.

  5. R5

    Nothing acknowledged is lost

    No 201 disappears when a pod, a node or a whole AZ fails.

    Aurora Multi-AZ; measured by the client log.

  6. R6

    One event per payment

    Exactly one event, delivered at least once. Merchants deduplicate by event id.

    A transactional outbox and a delivery table in the database.

  7. R7

    The ledger matches the bank

    Checked every day. Any difference raises an alert.

    A daily reconciliation job against the bank's settlement file.

Architecture

One database holds everything that must not be lost.

One Django codebase runs as three Deployments and a CronJob on EKS. Payments, the ledger, idempotency keys, the outbox and webhook deliveries all live in Aurora, so "where can data be lost?" has one answer. Pick something and watch where it goes.

1 / 6 The payment client, outside AWS, sends POST /v1/payments with an Idempotency-Key.

This is the target design. Locally today: the api and PostgreSQL, with ElasticMQ standing in for SQS. Dashed boxes exist only on DR days. Everything Kessai cannot lose sits inside the Aurora box. Read the full design.

ChoiceWhy
Aurora is the only system of recordPayments, ledger, keys, outbox and deliveries commit together. When something is lost, there is one place to look.
SQS FIFO instead of KafkaThe queue only carries events that are already safe in Aurora. It can be lost and refilled from the outbox.
No RedisNothing to keep in step with the database. Idempotency keys live in the same transaction as the payment.
A pilot light in OsakaA second full region costs money every hour. The Global Database needs r-class instances, so Osaka runs only on DR days.
Failing over is a human decisionRoute 53 health checks are ready, but moving a whole region is a business call. It is made by a person, and logged.
If Tokyo is lost, what happens to the events still in Tokyo's queue?

They don't matter. The outbox and the delivery table replicate to Osaka with the payments. The Osaka relay re-sends every event the delivery table hasn't marked as delivered, and merchants deduplicate by event id.

How it's scored

Counted from outside, where a failure can't hide it.

A system can't be trusted to report its own data loss. So the payment client runs outside AWS and keeps its own record of every payment Kessai acknowledged. After each drill, that record is compared with the database, row by row.

  1. Pay from outside. The client sends payments with a sequence number and an idempotency key, from a machine outside AWS.
  2. Write down every 201. Each acknowledged payment is appended to a local file. Nothing else counts.
  3. Break something. AWS FIS injects the drill's failure while the client keeps paying.
  4. Diff the log against the database. Acknowledged but missing means lost. Then the money rules are checked again.

The number of acknowledged payments missing from the database, plus the span of time they cover. The target for losing a pod, a node or a whole AZ is zero.

Built for Japan

Japanese rules, Japanese incidents. 日本の決済のルールで

Kessai is the kind of wallet PayPay, Merpay and Stripe run. It follows public rules rather than invented ones, and most of its drills are modelled on failures that really happened in Japan.

  • Yen has no minor unit. ¥1,200 is the integer 1200. There are no floats anywhere in the money code.
  • Tax by rate. Each payment records its 10 % standard and 8 % reduced amounts, as on a qualified invoice (インボイス制度, since 2023-10-01). The rounding rule (端数処理) comes from the National Tax Agency's guidance, not a guess.
  • Data stays in Japan. Tokyo runs everything; disaster recovery and backups go only to Osaka.
  • AZs pinned by ID. apne1-az1, az2 and az4, by ID rather than by name, because AZ names map to different zones in different accounts.
  • Real incidents. The 2019 apne1-az4 cooling failure, Zengin 2023, Mizuho 2021 and Askul 2025 each become a drill.

Glossary

New to this? Twelve words explain the whole project.

Every term on this page, in plain words. For the whole project end to end, with step-by-step diagrams and labs, read the study guide.

Idempotency key
A name the client gives one attempt to do something. Send it twice and the second is a replay, not a repeat. Stripe made the pattern common in payments.
Double-entry ledger
Money is never created or destroyed in the books: every movement is written as entries that cancel out. If all entries don't sum to zero, something is wrong.
Transactional outbox
Write the event in the same database transaction as the change it describes, then send it from there. The event can't be lost or invented.
At-least-once delivery
A message may arrive more than once, but never zero times. The receiver deduplicates by id.
Availability Zone (AZ)
One or more data centres in a region with their own power, cooling and network. Kessai spreads over three in Tokyo.
RPO
Recovery point objective: how much data a failure may lose. Here it's counted in acknowledged payments.
RTO
Recovery time objective: how long recovery may take. Here, from the fault to the first acknowledged payment.
Pilot light
A minimal copy of the system in another region: data replicating, compute mostly off until it's needed.
Reconciliation
Checking your own records against someone else's. Here, the ledger against the bank's settlement file.
AWS FIS
Fault Injection Service: AWS's tool for breaking things on purpose, with stop conditions that end a drill early.
Vault Lock
An AWS Backup setting that stops anyone, administrators included, from deleting recovery points early.
COE postmortem
Correction of Error: a postmortem format with impact, timeline, metrics, 5 Whys and action items with owners and dates.

Questions

Before you ask.

Is any real money involved?

No. The bank is a mock, the wallets are demo wallets, and there are no card numbers, so PCI DSS is out of scope, and there's no KYC. The rules it follows are real ones, so the drills mean something.

Has any drill run yet?

Not yet. Phase 0 builds the service on a laptop first. Each result will be published here and in the README as a measured number, with its postmortem, as each drill runs.

Why no Kafka?

Everything that must not be lost lives in Aurora. SQS FIFO only carries events that are already safe in the database, so it can be lost and refilled from the outbox. Kafka would add a second place where data lives.

What isn't in v1?

Authorise-then-capture, platform fees, merchant payouts and other currencies. v1 is top-ups, payments and refunds in yen.

What does it cost to follow along on AWS?

About $4–5 for an 8-hour Tokyo session, $9–12 for an Osaka DR day, and roughly $150–250 for the whole project if it runs only while someone is working on it. These are estimates from AWS Tokyo on-demand prices, not quotes.

Can I use it as a starting point?

Yes, it's MIT licensed. Treat it as a reference for how to build and prove a payments backend, not as a payment product: there is no card processing, KYC or compliance work in it.

How does it relate to Tasuki?

Same author, same production template. Tasuki is a delivery platform where the hard part is a system that moves; in Kessai the hard part is a system that must never lose anything.
