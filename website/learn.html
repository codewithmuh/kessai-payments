The big picture

What Kessai is, why it exists, what is built today, and where everything lives in the repository.

Start here

5 min
You will learn
  • What Kessai is, and the problem it is built to prove something about
  • How far the project has got, and how this guide marks what is real and what is planned
  • How to use the step-by-step diagrams and the checks at the end of each chapter
In plain words

Kessai is a practice bank-wallet app, built very carefully, then broken on purpose to prove it never loses money.

API
A way for programs to talk to each other over the internet. Kessai has no screens; apps send it requests.
Wallet
An account inside Kessai that holds yen for a customer or a merchant (a shop).
Acknowledged payment
A payment Kessai answered with "201 Created", which means "done, it is saved".
Availability Zone (AZ)
One group of data centres inside a region such as Tokyo. Three AZs means three separate buildings.
Drill
A planned test where something is broken on purpose to see what happens.
RPO / RTO
How much data was lost / how long it took to work again.

Kessai is a small wallet payments API in Japanese yen. A customer tops up a wallet from a (mock) bank, pays a merchant from that wallet, and the merchant can refund. Every movement of money is written to a double-entry ledger, merchants receive signed webhooks, and a nightly job checks the ledger against the bank. It is the kind of service PayPay, Merpay or Stripe run, cut down to the parts that matter for correctness.

The point is not the payments. The point is the proof. Kessai runs on Amazon EKS across three Availability Zones in Tokyo, with a disaster-recovery copy in Osaka. Then it gets broken on purpose in 12 failure drills: pods killed, a whole AZ powered off, the database failed over, the backups attacked, the region lost. Every drill is scored the same way: how many acknowledged payments were lost (the RPO) and how long recovery took (the RTO). "0 payments lost" is a result anyone understands, which is why the project chose payments as its subject.

It is a reference service, not a payment provider: no real money, no card numbers (so PCI DSS is out of scope) and no identity checks (KYC). It follows real rules anyway, such as Stripe's idempotency conventions and Japan's invoice tax rules, so that the drills test something real.

Where the project is today

Kessai is in phase 0. The Django service exists with its full runtime plumbing (health probes, metrics, JSON logs, graceful shutdown, safe behaviour during a database outage), CI and signed releases work, and all six Terraform stacks for AWS are written and pass static checks. The payments core itself (wallets, ledger, idempotency keys, webhooks, reconciliation) is the next thing to build, and nothing has been applied to AWS yet. The system in one picture

8 min
You will learn
  • Every component of the target design, and what each one does
  • Which of them exist today, which are written, and which are still to build
  • The one rule that shapes the whole design: a single system of record
In plain words

Think of one shop with one safe: every important thing goes in the same safe, so there is only one place to check.

System of record
The one place that holds the true copy of the data. In Kessai: the Aurora database.
Queue
A waiting line for messages. One program puts messages in, another takes them out.
Worker
A background program with no web page or API of its own. It does one job, again and again.
CronJob
A job that starts on a schedule, for example every night.
Test harness
Fake outside parties (a fake bank, a fake shop) used only for testing.

The whole design fits on one page. One Django codebase is built into one container image, and that image runs as several processes: the api that answers HTTP, an outbox-relay that moves events to a queue, a webhook-sender that delivers them to merchants, and a daily reconcile job. Three test-harness pieces play the outside world: a payment client outside AWS that sends payments and keeps score, a merchant-sim that receives webhooks, and a mock-bank that writes settlement files.

Everything that must not be lost lives in one Aurora PostgreSQL database: payments, ledger entries, idempotency keys, the outbox of events and the record of webhook deliveries. There is no Kafka and no Redis. That way the question "where can a payment be lost?" has exactly one answer, and every drill can check it.

Check yourself
Why is there no Kafka or Redis in Kessai?

Every extra store is another place data can live and be lost. With one system of record, "was this payment lost?" is answered by one database. The queue (SQS) only carries copies of events that are already safe in Aurora, so losing the queue loses nothing.

Which component keeps the score in a drill, and why does it run outside AWS?

The payment client. A system that is failing cannot be trusted to report its own failures, so the record of what Kessai acknowledged is kept on a machine the drill cannot break.

The seven money rules, one at a time. These ideas are independent of Django and AWS; you will meet them in every payments system. In docs/scope.md they are called R1 to R7, and every test and drill checks them.

4

Money is an integer (R1)

6 minDesigned
You will learn
  • Why floating-point numbers must never hold money
  • Why yen are stored as whole numbers
  • How Japanese consumption tax is split by rate on a receipt
In plain words

Computers keep most decimals slightly inexact, like writing 1/3 as 0.333. For money, "slightly" is not good enough.

Float (floating-point number)
A fast but inexact way computers store decimals. 0.1 + 0.2 becomes 0.30000000000000004.
Integer
A whole number with no decimal part: 1200, not 1200.00.
Minor unit
A currency's small coin, such as cents for dollars. The yen has none in use.
Consumption tax
Japan's sales tax: 10 % normally, 8 % for some food and drink.

Computers store most decimals approximately. In Python, 0.1 + 0.2 is 0.30000000000000004. Add a few thousand such amounts and the books stop balancing by a fraction of a yen, and nobody can say where it went. So the first money rule is blunt:

R1 · Integer yen

Amounts are integer yen. No floats anywhere. Enforced with integer database columns, and floats are banned in the money code.

The yen has no minor unit in use (there is no "cent" of a yen), so ¥1,200 is stored as the integer 1200. Stripe calls JPY a zero-decimal currency for the same reason. A currency with cents would store the amount in cents instead (€12.00 as 1200); Kessai v1 is yen only, so the question does not come up yet.

Tax, the Japanese way

Japan's consumption tax has two rates: 10 % standard and 8 % reduced (food and drink taken away, among others). Since 1 October 2023 the qualified invoice system (インボイス制度) asks sellers to show the amount and the tax for each rate. Kessai records that breakdown on every payment. Prices in Japan are shown tax-included, so the tax inside a price is price × rate ÷ (100 + rate).

When the tax does not divide exactly, a rounding rule (端数処理) applies once per invoice and rate. The scope says to take the exact rule from the National Tax Agency's guidance before coding it, so this guide does not guess it either.

In the code

The rule and its reasons: docs/scope.md, Money rules. The money model gets its own decision record (ADR) next on the roadmap.

Check yourself
PostgreSQL's NUMERIC type is exact. Why not store 1200.00 in a NUMERIC column?

It would be exact, but it allows fractions of a yen, which do not exist. An integer column makes the invalid state impossible to store, is smaller and faster, and matches how APIs like Stripe's send JPY.

How much tax is inside a ¥1,100 item at 10 %?

1100 × 10 ÷ 110 = ¥100.

The double-entry ledger (R2)

10 minDesigned
You will learn
  • How every movement of money becomes entries that cancel out
  • Why "all entries sum to zero" is the most useful check in the whole system
  • The two ways to keep a balance, and why Kessai's rules point to one of them
In plain words

Like moving money between two of your own bank accounts: one goes down, the other goes up by the same amount, and your total stays the same.

Ledger
The book where every movement of money is written down.
Entry
One line in the ledger: an account and an amount, plus or minus.
Account
A box that money sits in: a customer's wallet, a merchant's wallet, the bank.
Balance
How much money is in one account right now.
Invariant
A rule that must always be true. Here: all entries add up to zero.

Double-entry bookkeeping is 500 years old and still the best defence against lost money. The idea: money never appears or disappears. It moves from one account to another, and every movement is written as at least two entries whose amounts add up to zero.

R2 · Double-entry

Every money movement writes balanced entries, and all entries always sum to 0. Entries are written in the same database transaction as the movement, and the sum is checked in tests and after every drill.

Kessai needs only three kinds of account: a wallet for each customer, a wallet for each merchant, and bank clearing, the account that records money arriving from the bank. Step through one day.

Storing balances: two designs

  • Derive it. A balance is SUM(amount) over the account's entries. Always right, but every read scans more rows as history grows, and "is there enough money?" needs a lock over all of them.
  • Store it, and update it with the entries. The wallet row keeps a balance column, changed in the same transaction that writes the entries. Reads are instant and there is one row to lock. The entries remain the truth, and a check compares the two.

Rule R3 (next chapter) is enforced with "a row lock or a conditional update", which only makes sense for a stored balance on a wallet row. So the design points to the second option. The final choice belongs to the money-model ADR that comes next on the roadmap.

Signs or debit and credit?

Accountants write two columns, debit and credit. This guide uses signed amounts (+ in, − out) because they make the zero-sum rule obvious. They are the same idea written two ways.

Check yourself
A merchant refunds the full ¥1,200 instead. Which entries are written?

wallet · Komorebi −1,200 and wallet · Sato +1,200. The original payment entries stay untouched; the refund is its own movement.

After a drill, the sum of all entries is ¥1,200. What does that tell you?

Half of a movement was saved without the other half: a bug where entries were not written in one transaction. The zero-sum check found it without knowing which payment to look at.

Two payments at the same time (R3)

12 minDesigned
You will learn
  • How two simultaneous payments can spend the same money
  • Two fixes in PostgreSQL: SELECT … FOR UPDATE and a conditional UPDATE
  • Deadlocks, statement timeouts, and how the test for this rule works
In plain words

Two people share one card with ¥100 on it. Both check the balance at the same moment, both see ¥100, and both spend ¥100.

Concurrency
Several things happening at the same time.
Race condition
A bug that happens only when two things run at the same moment and their timing matters.
Transaction
A group of database changes that succeed together or fail together. Never half.
Row lock
A "busy, please wait" sign on one row of a table. Others wait until it is removed.
Isolation level
The rules for what one transaction can see of other transactions running at the same time.
Deadlock
Two transactions each waiting for the other's lock, so neither can ever continue.
R3 · Never below ¥0

A wallet never goes below ¥0. Enforced with a row lock or a conditional update in the same transaction. A test fires 200 parallel payments at a balance that covers 50.

The obvious code reads the balance, checks it, and writes the new balance. On its own that is correct. With two requests at the same moment it is not, because PostgreSQL's default isolation level, READ COMMITTED, lets both read the same committed value before either writes. Sato has ¥100 and two ¥100 payments arrive together.

Both fixes look like this in Django. The models do not exist yet, so read this as a sketch:

sketch · not in the repository yet
from django.db import transaction
from django.db.models import F

# Fix 1: lock the row, then check and write
with transaction.atomic():
    wallet = Wallet.objects.select_for_update().get(pk=wallet_id)
    if wallet.balance < amount:
        raise InsufficientFunds()
    wallet.balance -= amount
    wallet.save(update_fields=["balance"])
    # payment, ledger entries, idempotency key and outbox row: same transaction

# Fix 2: one conditional statement; 0 rows updated means "not enough money"
updated = Wallet.objects.filter(pk=wallet_id, balance__gte=amount).update(balance=F("balance") - amount)
if updated == 0:
    raise InsufficientFunds()

Two traps that come with locks

  • Deadlocks. A payment touches two wallets (customer, then merchant) and a refund touches the same two the other way round. If a payment locks Sato then Komorebi while a refund locks Komorebi then Sato, each waits for the other forever; PostgreSQL detects it and kills one (SQLSTATE 40P01). The standard cure is to always lock rows in the same order, for example by ascending wallet id. In Kessai's code a deadlock is treated as a bug and stays a 500, not a "retry later" 503 (see core/database.py).
  • Locks held too long. A slow query holding a lock blocks every other payment on that wallet. The service sets statement_timeout to 5 seconds (DB_STATEMENT_TIMEOUT_MS), so a stuck statement is cancelled; that error (57014) becomes a 503 the client can retry.

How R3 is tested

The test fires 200 payments in parallel at a wallet that can afford 50, then checks that exactly 50 succeeded and the balance is exactly ¥0. SQLite cannot reproduce row locks, so such tests carry the pytest marker postgres and run against a real PostgreSQL 17, which CI starts as a service. The landing page has an animation of this test, with and without the lock.

In the code

The marker: [tool.pytest.ini_options] markers in pyproject.toml. The timeout: DB_STATEMENT_TIMEOUT_MS in settings.py. The PostgreSQL service in CI: the python job in ci.yml.

Check yourself
Why does the conditional UPDATE not need a separate SELECT … FOR UPDATE?

An UPDATE takes the row lock itself. Under READ COMMITTED, a second UPDATE waiting on that lock re-evaluates its WHERE clause against the newly committed row before it changes anything, so the check and the write happen atomically.

Would SERIALIZABLE isolation also fix the race?

Yes: one of the two transactions would fail with a serialization error and must be retried. It works, but every conflicting payment becomes an error and a retry. A row lock makes them queue instead, which is simpler for a hot wallet.

Why must the R3 test run on PostgreSQL and not SQLite?

SQLite locks the whole database file for writes and has no row-level locks or SELECT … FOR UPDATE. A test there would pass for the wrong reason.

Safe retries: idempotency keys (R4)

12 minDesigned
You will learn
  • Why a client can never know for sure whether a payment happened
  • How an idempotency key turns "retry" from dangerous into safe
  • Why the key must be saved in the same transaction as the payment
In plain words

Pressing a lift (elevator) button five times still calls the lift once. That is idempotent: doing it again does not change the result.

Idempotent
Doing something twice has the same effect as doing it once.
Idempotency key
A unique name, like an order number, that the app puts on one payment attempt. The server remembers it, so a repeat with the same name is recognised and not paid again.
Retry
Sending the same request again after it seemed to fail.
Timeout
Giving up waiting for an answer. It does not tell you whether the other side did the work.
Replay
Sending back the answer that was saved the first time.

A request can fail in three places: before it reaches the server, inside the server, or on the way back. From the client's side the third case looks exactly like the first two: a timeout. The payment may or may not have happened. Retrying blindly can charge twice; never retrying can lose a sale. An idempotency key removes the dilemma: the client names each attempt, and the server promises that one name produces at most one payment.

R4 · One key, one payment

The same key and body replays the saved response. The same key with a different body is an error. Keys are kept 24 hours. The key is stored in the same transaction as the payment. This follows Stripe's idempotent requests.

Why the key must be in the same transaction

Suppose the key were saved after the payment, in a second step. A crash between the two leaves a payment with no key, and the retry pays again. Saved first, a crash leaves a key with no payment, and the retry replays a response for a payment that never happened. Only one transaction gives "both or neither".

This matters most during a database failover. The service's outage middleware explains it in its own words: when a request fails because the database went away, the transaction has rolled back, so the client may retry. But if the COMMIT reached the server just before the connection died, the payment does exist and the client cannot tell. The same key makes both cases safe: the retry either replays the stored response or creates the payment once. Drill 5 tests exactly this.

In the code

The docstring of DatabaseUnavailableMiddleware in core/middleware.py, and the 503 body in database_unavailable() in core/errors.py, which tells clients "a payment is safe to retry with the same Idempotency-Key".

What gets stored with a key

  • The key itself, scoped to the caller (two merchants may pick the same string).
  • A fingerprint of the request: method, path and a hash of the body.
  • The response status and body to replay, and when it was created (for the 24-hour expiry).

A 503 database_unavailable saves nothing, because its transaction rolled back. The retry runs fresh.

Check yourself
Is GET /v1/payments/{id} in need of an idempotency key?

No. A read changes nothing, so repeating it is naturally safe. Keys are required on the three money endpoints: top-ups, payments and refunds.

The app generates a new key on every retry. What goes wrong?

Every retry looks like a new payment, so a lost response followed by a retry charges twice. The key must stay the same for every retry of one attempt.

Where in drill 5 does R4 get tested?

The client keeps retrying the same keys while AWS FIS fails the Aurora writer over. The pass condition is "one payment per key" and zero acknowledged payments lost.

Telling the merchant: outbox and webhooks (R6)

15 minDesigned Queues written
You will learn
  • The dual-write problem, and why "save, then publish" loses events
  • The transactional outbox pattern, and how SQS FIFO carries the events
  • Retries, dead-letter queues, signatures and deduplication on the merchant side
In plain words

A shop writes "send the customer a receipt" on the same order form as the sale. Later a clerk posts a receipt for every form. Even if the cashier faints right after the sale, no receipt is forgotten.

Event
A short message that says something happened, such as "payment succeeded".
Webhook
An HTTP request Kessai sends to the merchant's server to tell it about an event.
Outbox
A table in the database where events wait until they are sent.
Dual write
Saving the same fact in two systems that cannot be updated together.
Deduplicate (dedupe)
Ignoring a message you have already seen.
Dead-letter queue
A side queue for messages that failed too many times, kept so someone can look at them and send them again.

When a payment succeeds, the merchant must hear about it through a payment.succeeded webhook. That means writing to two systems, the database and the queue, and no transaction spans both. This is the dual-write problem, and it is the most common way event-driven systems lose data.

R6 · One event per payment

Every payment creates exactly one event, delivered at least once; merchants deduplicate by event id. Enforced with a transactional outbox and a delivery table in the database.

Signed webhooks

A merchant must be able to prove a webhook came from Kessai and was not replayed by someone who captured it. The usual scheme (Stripe's) sends a header with a timestamp and an HMAC-SHA256 signature of timestamp + "." + body, made with a secret only Kessai and that merchant share. The merchant recomputes it, compares in constant time, and rejects anything older than a few minutes. Kessai's exact header is still to be designed; the idea will be the same:

merchant side · Stripe-style verification
import hashlib, hmac, time

def verify(header: str, body: bytes, secret: bytes, tolerance_s: int = 300) -> bool:
    parts = dict(item.split("=", 1) for item in header.split(","))   # "t=1760929449,v1=5f0a..."
    timestamp, signature = int(parts["t"]), parts["v1"]
    if abs(time.time() - timestamp) > tolerance_s:
        return False                                          # too old: possibly a replay
    expected = hmac.new(secret, f"{timestamp}.".encode() + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)          # constant time

Two more safety nets

  • Catch-up. GET /v1/events?since= lets a merchant fetch anything it missed, straight from the database.
  • Region loss. The outbox and deliveries tables replicate to Osaka with the payments. If Tokyo is lost, events still in Tokyo's queue do not matter: the Osaka relay re-sends every event not marked delivered, and merchants dedupe.
In the code

Queues: infra/data/sqs.tf and dev/elasticmq.conf. The relay and sender's AWS permissions (send only; receive, delete and change visibility only): infra/data/workload-iam.tf.

Check yourself
Why not let the api publish to SQS inside the database transaction?

The publish is not part of the transaction. If the transaction then rolls back, the message is already sent: a phantom event. Only rows written in the transaction share its fate.

A merchant processes evt_8G twice and ships two coffees. Whose bug is it?

The merchant's. At-least-once delivery is part of the contract, and the event id exists so receivers can drop repeats. Kessai's merchant-sim does exactly that, and counts duplicates as a drill metric.

Why one message group per merchant rather than one group for the whole queue?

A single group would deliver every event in strict global order, so one merchant that is down would hold up everyone. Per-merchant groups keep order where it matters and isolate slow receivers.

Why may the api not send 201 before COMMIT returns?

Health checks and database outages

12 minBuilt
You will learn
  • The difference between liveness and readiness, and why liveness never checks the database
  • The readiness grace window: why a pod stays ready while the database is failing over
  • Which database errors count as an outage, by SQLSTATE
In plain words

Liveness asks "is the cashier awake?". Readiness asks "should customers queue at this till right now?".

Probe
A small check Kubernetes makes on a container every few seconds.
Liveness
Is the program stuck? If yes, restart it.
Readiness
Should this copy receive traffic now? If no, the load balancer skips it.
Grace period
Extra time allowed before acting.
503 + Retry-After
"Busy right now, please try again in N seconds."
SQLSTATE
The database's five-character error code.

Kubernetes asks two questions. Liveness: is this process stuck and in need of a restart? Readiness: should this pod receive traffic right now? Kessai answers them at /healthz and /readyz.

  • /healthz never checks dependencies. If it checked the database, a database outage would make every pod fail liveness, Kubernetes would restart all of them at once, and the outage would become a restart storm.
  • /readyz fails in two cases: during shutdown (chapter 13), and when the database has been failing for longer than the grace period.

Why not fail readiness the moment the database fails?

Every api pod shares one Aurora writer. If readiness failed on the first failed check, a failover would take every pod out of the load balancer within seconds. Clients would get connection errors with no 503 and no Retry-After, and the availability numbers would record nothing, because the requests never reached Django. So the pod stays in rotation and answers each request with a proper 503 + Retry-After, which clients retry and the metrics count.

Two more rules in DatabaseReadiness

  • A pod that has never reached the database is not ready at all. A new pod with a wrong DATABASE_URL takes no traffic during a rollout, so a bad deploy cannot replace healthy pods.
  • The clock is per process. Each gunicorn worker keeps its own failure clock (with a lock for its threads), so two calls to /readyz may report slightly different database_failing_for_s. The clock is injectable, which is how the tests move time without sleeping.

Which errors are an outage?

psycopg reports both outages and some bugs as OperationalError (a deadlock is one), so the exception class is not enough. The SQLSTATE code the server sent decides:

SQLSTATEMeaningReason labelTypical cause
57P01admin_shutdownshutdownFailover or instance reboot
57P02crash_shutdownshutdownAnother backend crashed; the server restarts
57P03cannot_connect_nowshutdownThe server is starting or recovering
25006read_only_sql_transactionread_onlyConnected to a reader, not the writer: an old connection after a failover
53300too_many_connectionstoo_many_connectionsEvery connection slot is taken
57014query_canceledtimeoutThe 5-second statement timeout ran out
08xxxconnection exceptionconnectionThe connection broke
noneno answer at allconnectionRefused, reset or timed out before the server spoke
Everything else (unique violation, bad SQL, deadlock 40P01…) is a bug or a conflict: it stays a 500.

The 25006 case is the subtle one. After a failover the old writer comes back as a reader. A connection opened before the failover, or a DNS answer cached from before it, can still point there, and writes fail as "read-only". Treating that as a short outage, while connections are health-checked and renewed, lets the retry land on the new writer.

Check yourself
Set READINESS_DB_GRACE_SECONDS to 0. What happens during a failover?

Every pod fails readiness at the first failed check and the load balancer removes all of them. Clients see connection errors or 502/503s from the load balancer with no Retry-After, and the api's own metrics see nothing.

Why does /healthz return {"status": "ok"} even when the database is down?

Liveness asks "is this process alive?", and it is. Restarting it would not fix the database and would turn one outage into many restarts.

Why a second account

An account is AWS's strongest wall. Whoever controls the workload account, even its root user, has no rights inside the backup account. Cross-account backup copies need both accounts in the same AWS Organization, with cross-account backup turned on once from the management account. The recommended layout is three accounts: a management account that runs nothing, the workload account and the backup account.

Fencing the apply role

The apply role gets PowerUserAccess (everything except IAM, Organizations and account settings), then IAM is added back narrowly. Three tricks are worth learning:

  • Name scoping. It may manage IAM roles and policies only if their names start with kessai-. Every stack names its roles that way, and a variable validation enforces the prefix.
  • An explicit Deny narrows a broad Allow. PowerUserAccess alone would allow creating any service-linked role. A Deny with StringNotEquals on the service name limits it to the six services Kessai needs (EKS, node groups, ELB, Auto Scaling, spot, RDS). In IAM, an explicit Deny always wins.
  • No self-promotion. The CI roles are named kessai-github-*, which matches the prefix. A Deny on everything except Get* and List* for those roles stops the apply role from editing its own policies to grant itself more.

Its policy lets the account's IAM decide who uses it, and, once the backup account exists, lets that account decrypt and create grants only for AWS services (kms:GrantIsForAWSResource), so AWS Backup can copy snapshots. The backup account can never change or delete the key. It costs about $1 a month.

In plain words

SLI
A measurement, such as the share of requests that worked.
SLO
The target for that measurement over a period, such as 99.9 % over 28 days.
Error budget
How much failure the target allows.
Burn rate
How fast that allowance is being used up.

Phase 1 adds Prometheus, Grafana and OpenTelemetry, with SLOs and burn-rate alerts. The concepts first:

  • SLI (indicator): a measurement, such as "the share of payment requests that did not return 5xx". The api's http_requests_total already provides it (chapter 14).
  • SLO (objective): a target for the SLI over a window, such as 99.9 % over 28 days.
  • Error budget: what the SLO allows to fail. 0.1 % of 28 days is about 40 minutes (28 × 24 × 60 × 0.001 = 40.3) of complete failure, or more time at partial failure.
  • Burn rate: how fast the budget is being spent. A burn rate of 1 spends exactly the budget over the window; 14.4 spends 2 % of a 30-day budget in one hour.
Why alert on burn rate

Paging on every error wakes people for noise; paging on a 28-day average notices too late. The Google SRE workbook's pattern uses two windows per alert: page when the budget burns fast over both a long and a short window (for example 14.4× over 1 hour and 5 minutes), and open a ticket when it burns slowly (for example 6× over 6 hours and 30 minutes). The short window makes the alert stop soon after the problem does.

The concrete SLOs for Kessai are not written yet; they come with phase 1, along with dashboards kept as code and alerts that link to runbooks. Drill 12 checks one of them under load: "the payment SLO holds; the batch job slows down instead".

Lab 3: time an Aurora failover

45 minNeeds Lab 2
You will
  • Watch the writer move from one AZ to another, from inside the VPC
  • Measure how long writes were unavailable, the number drill 5 cares about
  • See why the api's 25006 (read-only) handling exists

This is the database half of drill 5, without the app. Aurora only accepts connections from EKS nodes, so you run psql in a throwaway pod. The only nodes are the tainted system nodes (Karpenter is not installed yet), so the pod needs a toleration.

1. Start a psql pod (with a session from Lab 2 running)

WRITER=$(terraform -chdir=infra/data output -raw db_writer_endpoint)
SECRET=$(terraform -chdir=infra/data output -raw db_secret_arn)
PGPASSWORD=$(aws secretsmanager get-secret-value --secret-id "$SECRET" --query SecretString --output text | jq -r .password)

kubectl --context kessai run psql --image=postgres:17-alpine --restart=Never \
  --env="PGPASSWORD=$PGPASSWORD" --env="WRITER=$WRITER" \
  --overrides='{"spec":{"tolerations":[{"key":"CriticalAddonsOnly","operator":"Exists"}]}}' \
  -- sleep 3600
kubectl --context kessai wait --for=condition=Ready pod/psql --timeout=120s
kubectl --context kessai exec -it psql -- sh

2. Inside the pod: ask the writer who it is, every second

while true; do
  printf '%s  ' "$(date -u +%H:%M:%S)"
  psql "host=$WRITER dbname=kessai user=kessai_admin sslmode=require connect_timeout=2" \
       -Atc "select inet_server_addr(), pg_is_in_recovery()" 2>&1 | head -n 1
  sleep 1
done
# 03:12:01  10.50.108.23|f      <- the writer's IP; f = not a replica

3. In a second terminal: fail over

aws rds failover-db-cluster --db-cluster-identifier kessai
# afterwards, AWS's own timeline:
aws rds describe-events --source-type db-cluster --source-identifier kessai --duration 15 \
  --query 'Events[].[Date,Message]' --output table

4. Read the result

  • Last good line before the errors, first good line after: the gap is how long writes were unavailable. Kessai's target is a writer back within 60 seconds.
  • The IP changes from a 10.50.108.x address (az4) to 10.50.109.x (az1), or the other way round: the writer moved AZ.
  • If you ever see |t after the failover, the writer endpoint's DNS still pointed at the old writer, now a replica. That is the SQLSTATE 25006 case from chapter 12, and why the api treats "read-only" as a short outage.

Glossary

reference
Access entry (EKS)
The way an IAM principal is given access to an EKS cluster, managed through the EKS API instead of the old aws-auth ConfigMap.
ADR
Architecture Decision Record: a short document that records one significant decision, its context and its consequences. Kept in docs/adr/.
ALB
Application Load Balancer. In Kessai it is created by the AWS Load Balancer Controller from the api's Ingress.
At-least-once delivery
A message may arrive more than once, never zero times. Receivers deduplicate by id.
Availability Zone (AZ)
One or more data centres in a region with independent power, cooling and network. Kessai uses three in Tokyo.
AZ ID
A zone's fixed identifier, such as apne1-az4, the same physical zone in every account (unlike names such as ap-northeast-1a).
Burn rate
How fast an error budget is being spent, relative to spending it exactly over the SLO window.
COE postmortem
Correction of Error: impact, timeline, metrics, 5 Whys, and action items with owners and dates.
cosign (keyless)
Sigstore's tool for signing container images with a short-lived certificate tied to a CI identity, instead of a long-lived key.
Dead-letter queue (DLQ)
Where a message goes after too many failed attempts, to be inspected and replayed later.
Double-entry ledger
Every movement of money is recorded as entries that sum to zero; money moves between accounts and is never created.
Error budget
The amount of failure an SLO allows over its window, for example about 40 minutes for 99.9 % over 28 days.
External Secrets
A Kubernetes operator that copies secrets from AWS Secrets Manager into Kubernetes Secrets.
FIFO queue (SQS)
A queue that keeps order within a message group and drops duplicates by deduplication id for 5 minutes.
FIS
AWS Fault Injection Service: runs experiments that break things on purpose, with stop conditions.
Global Database (Aurora)
An Aurora cluster replicated to another region at the storage layer, usually under a second behind.
Graceful shutdown
Stopping a server by refusing new work, finishing work in flight, then exiting.
Idempotency key
A name the client gives one attempt, so the server performs it at most once however often it is retried.
Karpenter
A Kubernetes node autoscaler that launches EC2 instances directly when pods need room.
KMS key
An encryption key in AWS Key Management Service. Kessai's money-data key encrypts all money data.
Liveness probe
Kubernetes asks "is this process stuck?"; failing it restarts the container. Kessai's never checks dependencies.
NAT gateway
Lets resources in private subnets reach the internet without being reachable from it.
Object Lock
S3's write-once-read-many setting; in compliance mode no one can delete a locked object version before its retention ends.
OIDC (GitHub to AWS)
A signed identity token from GitHub that AWS STS exchanges for temporary credentials, so no keys are stored.
Outbox (transactional)
Writing an event as a row in the same transaction as the change it describes, then sending it from there.
Pilot light
A minimal copy in another region: data replicating, compute off until it is needed.
PITR
Point-in-time restore: restoring a database to any second within its backup retention window.
Pod Identity (EKS)
Gives a Kubernetes service account an IAM role, through an agent on each node.
Qualified invoice
Japan's invoice system (since 2023-10-01) that shows the tax for each consumption-tax rate.
Readiness probe
Kubernetes asks "should this pod get traffic?"; failing it removes the pod from the load balancer.
Reconciliation
Comparing your records with someone else's: the ledger with the bank's settlement file.
release-please
A tool that turns Conventional Commits into version numbers, a changelog and release pull requests.
Rekor
Sigstore's public transparency log, where every keyless signature is recorded.
RPO
Recovery point objective: how much data a failure may lose. In Kessai, acknowledged payments lost and the time they span.
RTO
Recovery time objective: how long recovery may take. In Kessai, from the fault to the first acknowledged payment.
SBOM
Software bill of materials: the list of every package and version inside an image.
SLI / SLO
A service-level indicator is a measurement; an objective is the target for it over a window.
SQLSTATE
PostgreSQL's five-character error code, such as 57P01 (shutdown) or 40P01 (deadlock).
Vault Lock
AWS Backup's setting that stops recovery points being deleted before their retention ends; permanent in compliance mode.
Visibility timeout
How long SQS hides a received message from other consumers before it can be received again.
Zonal shift
An Amazon Application Recovery Controller feature that moves load-balancer and EKS traffic away from one AZ.
